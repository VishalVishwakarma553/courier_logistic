Courier Platform System Architecture

How the platform is built, deployed and scaled: the services that run it, how every courier plugs in, how a booking travels from quote to delivery, and how the system stays secure and available.

Section 1

What the architecture is built around

Many couriers, one platform

Each courier is a plug-in behind one common interface. A new courier is a new adapter plus configuration from the admin panel.

Maximum automation

Every step after booking (AWB, label, pickup, tracking, notifications, billing) runs as a background job with automatic retries.

Honest fallbacks

Each courier declares what its integration supports. Anything unsupported becomes a manual task, and the screens say so.

Scalable

API servers and background workers scale separately. Database, cache and file storage are managed AWS services.

Reliable

Safe-to-repeat operations, retries with backoff, isolation of failing couriers, a standby database and point-in-time recovery.

Secure

Role-based access, encrypted courier credentials, strict separation between customers, a full audit trail, data kept in India.

Modular monolith with separate workers

One codebase divided into strict modules (booking, rates, tracking, billing and so on), deployed as separate services that scale independently. This gives the scaling benefits of microservices where they matter, without the operating cost. Any module can be split out later without a rewrite.

Section 3

Codebase structure

A single repository with shared code between the web app and the server.

courier-erp/
├── apps/
│   ├── web/                  Next.js (customer, admin, public tracking)
│   └── server/               NestJS: one codebase, two entrypoints
│       ├── src/main.api.ts       → starts the REST API
│       ├── src/main.worker.ts    → starts the queue processors
│       └── src/modules/
│           ├── auth/  customers/  couriers/  rates/
│           ├── booking/  pickup/  tracking/  billing/
│           └── notifications/  support/  reports/  admin/
├── packages/
│   ├── courier-adapters/     one folder per courier + the manual adapter
│   ├── shared/               validation schemas, types, status list (web + server)
│   └── pdf/                  label, invoice, commercial-invoice templates
├── database/                 schema.sql, migrations
└── infra/                    Terraform (AWS), Dockerfiles, CI/CD
  • A module touches only its own tables and uses other modules only through their service interfaces.
  • Modules communicate through events such as shipment.manifested and shipment.delivered. Billing, notifications and statistics subscribe to them, so booking doesn't depend on them.
  • Validation rules are shared by the web app and the API, so the two can never disagree.
Section 4

Courier integration layer

The most important part of the system. Every courier, with or without an API, implements the same interface:

export interface CourierAdapter {
  readonly code: string;                       // 'delhivery', 'bluedart', 'manual'
  readonly capabilities: CourierCapabilities;  // what this integration really supports

  checkServiceability(req): Promise<ServiceabilityResult>;
  createShipment(req): Promise<CreateShipmentResult>;  // → AWB (+ label if provided)
  track(awbs: string[]): Promise<TrackingUpdate[]>;

  getTransitTime?(req): Promise<TatResult>;
  getLabel?(awb): Promise<LabelResult>;
  schedulePickup?(req): Promise<PickupResult>;
  cancel?(awb): Promise<CancelResult>;
  parseWebhook?(headers, body): TrackingUpdate[];     // verifies the signature first
}
flowchart LR
  B[Booking / Pickup / Tracking modules] --> R[Adapter registry]
  R --> D[DelhiveryAdapter]
  R --> BD[BlueDartAdapter]
  R --> DH[DhlAdapter]
  R --> M[ManualAdapter]
  D & BD & DH --> H[Shared HTTP client<br/>timeout · retry · circuit breaker · logging · masking]
  H --> X[Courier APIs]
  M --> DB[(AWB stock, uploaded<br/>pincodes, manual tracking)]
ConcernHow it's handled
Selecting an adapterEach courier's configured adapter is looked up in a registry. Credentials are loaded from the database, decrypted through AWS KMS and cached in memory for 5 minutes.
Missing capabilityThe calling module checks the capabilities first. If a courier has no pickup API, a manual pickup task is created for operations staff instead.
TimeoutsServiceability and quotes: 3 seconds. AWB, pickup and tracking: 15 seconds.
RetriesOnly on network errors, server errors and rate limits, with growing delays. Never on validation errors.
Courier outageAfter repeated failures the courier is marked temporarily unavailable for 60 seconds. Quotes skip it and booking explains why. Everything else keeps working.
LoggingEvery courier request and response is logged, with secrets and personal data masked.
Status mappingAdapters return the courier's own codes; the tracking module maps them to the platform's 18 statuses.
TestingEvery adapter is tested against the courier's sandbox, plus recorded responses for automated builds.

Adding a new courier: write one adapter (typically 2–5 days, depending on the quality of the courier's API), register it, then configure services, credentials, pincodes and status mappings from the admin panel.

Key flows

Quote and booking

sequenceDiagram
  autonumber
  actor U as Customer
  participant W as web
  participant A as api
  participant RE as Rate engine
  participant C as Courier APIs
  participant DB as PostgreSQL
  participant Q as Queue (Redis)
  participant WK as worker
  U->>W: Enter pickup, delivery, weight, dimensions, type
  W->>A: POST /v1/quotes
  A->>RE: Find eligible services for this customer
  par each enabled courier service
    RE->>C: serviceability / TAT (3 s timeout, cached)
  end
  RE->>DB: rate cards, zone, surcharges
  A-->>W: Options: courier, ETA, price (quote valid 15 min)
  U->>W: Choose a courier, confirm
  W->>A: POST /v1/shipments + Idempotency-Key
  A->>DB: BEGIN: insert shipment, lock wallet, debit ledger, COMMIT
  A->>Q: enqueue shipment.create
  A-->>W: booking_ref (waits up to 10 s for the AWB)
  Q->>WK: shipment.create
  WK->>C: createShipment → AWB (+ label)
  WK->>DB: status = manifested, save AWB
  WK->>Q: label, pickup, booking notification
  W-->>U: AWB + label download
  • The customer usually gets the AWB on the same screen. If the courier is slow, they see "Booking confirmed, AWB is being generated" and the page updates when it's ready.
  • If AWB generation fails after every retry, the booking is marked failed, the wallet is refunded automatically, and operations staff are alerted.
  • The quoted price is locked for 15 minutes, so the price charged is the price shown.

Tracking: webhooks and polling

sequenceDiagram
  autonumber
  participant C as Courier
  participant A as api
  participant DB as PostgreSQL
  participant Q as Queue
  participant WK as worker
  participant N as Notifications
  alt Courier supports webhooks
    C->>A: POST /v1/webhooks/{courier}
    A->>A: verify signature
    A->>DB: store raw event
    A->>Q: enqueue tracking.process
    A-->>C: 200 OK (under 200 ms)
  else Polling
    Note over Q: every 5 min, shipments due for a check are picked up
    Q->>WK: tracking.poll (batched per courier)
    WK->>C: track(awbs)
  end
  WK->>WK: map courier code to platform status
  WK->>DB: insert tracking event (duplicates ignored)
  WK->>DB: update shipment status if the move is valid
  WK->>Q: emit shipment.status_changed
  Q->>N: notify (out for delivery, delivered...)
  • Adaptive polling: out for delivery every 30 minutes, in transit every 2 hours, pickup pending every hour, delivered never. This keeps courier API usage low.
  • No backwards moves: an old event that arrives late (such as "in transit" after "delivered") is kept in the history but never changes the current status.
  • Every webhook is stored before processing, so it can be replayed if processing fails.

Pickup

After AWBs are generated, the day's shipments from the same address and courier are grouped into one pickup request. If the courier has no pickup API, or the request fails after retries, a manual pickup task appears on the operations dashboard with an alert.

Section 7

API design

TopicConvention
StyleREST and JSON under /api/v1, with Swagger documentation generated from the code
Login15-minute access token plus a rotating refresh token in a secure cookie. Optional API keys for customers who book from their own systems.
PermissionsChecked on every route. The customer is always taken from the login token, never from the request, so no customer can see another's data.
Customer vs staffSeparate response formats. Purchase cost and margin never appear in customer responses.
Repeat-safe requestsAn Idempotency-Key header is required for booking, payment and wallet requests
PaginationCursor-based, so lists stay fast at millions of rows
ErrorsOne format with a stable code, such as COURIER_UNAVAILABLE, and a readable message
Rate limitsPer user and per IP. Public tracking: 30 lookups per minute per IP.
Long operationsExports and bulk uploads return a job ID to check progress
Section 8

Security

LayerControls
NetworkAWS WAF in front of everything. Application, database and Redis in private subnets; only the load balancer is public.
TransportTLS everywhere, including database and Redis connections
LoginStrong password hashing, account lockout, optional two-factor login (required for Super Admin), session revocation
AccessRole-based permissions editable from the admin panel; every query limited to the customer's own data
SecretsCourier credentials encrypted with keys held in AWS KMS. Application secrets in AWS Secrets Manager, never in code.
FilesPrivate storage. Downloads only through short-lived links issued after a permission check.
WebhooksSignature verification, plus IP allowlists where the courier publishes them
Personal dataMasked in logs, deleted on a retention schedule, stored in AWS Mumbai to keep data in India (DPDP Act 2023)
AuditEvery admin change, login, export and manual status correction is recorded

Section 10

Scalability and reliability

SituationWhat happens
More usersMore web and API containers are added; they hold no state of their own
More shipmentsMore worker containers are added; throughput grows almost in step
Heavy reportsServed from the read replica and pre-calculated daily totals
Database growthMonthly partitions for logs and tracking, small indexes for work queues
A courier goes downThat courier is isolated; others keep working and its jobs retry later
A burst of webhooksEach is stored and queued in under 200 ms, then processed at a controlled rate
An AWS zone failsDatabase, Redis and every service already run in two zones
Disaster recoveryAt most 5 minutes of data at risk, service restored within 1 hour, restores tested quarterly, daily backup copied to a second region

Proposed performance targets

< 3 sRate quote across all couriers (p95)
< 10 sBooking confirmed with AWB (p95)
< 1 sPublic tracking page (p95)
< 2 minTracking freshness, webhook couriers
99.9%Monthly availability

Alerts go to email, SMS or Slack when: a courier's API error rate exceeds 10% for 5 minutes, queues back up, AWB generation fails, webhook processing fails, the database runs hot or low on space, a scheduled job fails, or payment callbacks fail.

DecisionChosenAlternativeWhy

BackendNestJS (TypeScript)Laravel (PHP)One language across web, API and shared validation. Laravel with Horizon is a valid equivalent if PHP is required.

Section 14

Open questions for the client

  1. Is there an existing AWS account, or a preference for another cloud provider?
  2. Will any customers book through an API from their own websites or ERPs? This decides whether customer API keys are in phase 1.
  3. Is there an existing domain and email-sending domain? Both are needed for email delivery and WhatsApp business verification.
  4. What peak load is expected, for example during festival season? This sets the auto-scaling limits.
  5. Who handles operations alerts outside office hours?
