Section 1

Design principles

One shipment model for every courier

Each courier's own status codes are mapped onto 18 platform statuses, so dashboards, reports and notifications work the same way for every courier.

Couriers are data, not code

Adding a courier means adding rows: services, credentials, serviceable pincodes, status mappings. No database change is needed.

History is never rewritten

Addresses and prices are copied onto the shipment at booking. The wallet ledger and tracking history only ever get new rows.

The database blocks bad data

Duplicate AWBs, double bookings, double wallet charges and repeat COD payouts are rejected by the database even if the application has a bug.

Money is exact

Every amount is stored as an exact decimal. Weight is stored in whole grams. Floating-point numbers are never used for money.

Internal cost stays internal

Purchase cost is stored beside the selling price, but only staff roles can see it. Customers see their approved selling rate only.

Section 4

Key decisions

Shipment type is split into three fields

The requirement lists "Prepaid, COD, To Pay, Reverse Pickup, International" as one list. These are independent: a reverse pickup can be prepaid, and an international shipment can be prepaid. The database stores payment_mode (prepaid, cod, to_pay), direction (forward, reverse) and is_international. The booking screen can still show the five familiar options.

One status list for every courier

Each courier sends different codes. Every code is translated into one of 18 platform statuses through an admin-editable mapping table. Codes with no mapping are logged and flagged for review.

Normal delivery route
  1. draft
  2. booking_confirmed
  3. manifested
  4. pickup_scheduled
  5. picked_up
  6. in_transit
  7. arrived_at_hub
  8. customs_clearance
  9. out_for_delivery
  10. delivered
Off the normal route
delivery_failed exception rto_initiated rto_in_transit returned_to_sender booking_failed cancelled lost

Dashed stop: international shipments only. AWB generation moves a booking to manifested.

How a price is calculated

  1. Zone. Zone rules are checked in priority order: same city, same state, metro to metro, special region, rest of India. International zones are set by destination country.
  2. Chargeable weight. The higher of actual weight and L × B × H ÷ volumetric divisor, with the divisor set per courier service.
  3. Freight. The matching weight slab gives a base rate plus a rate for each additional weight unit.
  4. Surcharges. Fuel percentage, COD (percentage or a minimum, whichever is higher), out-of-delivery-area, handling, insurance.
  5. Selling price for this customer. Their own selling rate card if one exists, otherwise purchase cost plus their markup, otherwise the default selling card.
  6. GST. SAC 996812. CGST + SGST or IGST depending on the place of supply.

Both cost and selling price are frozen onto the shipment at booking. A later rate change never alters a past shipment, and profit is exact per shipment.

Wallet and ledger

The ledger is the source of truth and is append-only. The wallet balance is a cached copy for fast reads. A booking charge happens in one transaction:

BEGIN;
SELECT balance FROM wallets WHERE customer_id = $1 FOR UPDATE;  -- one booking at a time per customer
-- check balance (prepaid) or credit limit (credit customers)
INSERT INTO ledger_entries (...) VALUES (... 'debit', 'shipment', shipment_id ...);
UPDATE wallets SET balance = balance - $amount WHERE customer_id = $1;
COMMIT;

Couriers without an API

Each courier records its integration mode (api, manual or hybrid) and exactly what its integration supports. The screens use this to show customers and staff which steps are automatic. For manual couriers:

  • serviceable pincodes come from an Excel upload
  • AWB numbers come from a pre-allotted series held in courier_awb_stock
  • pickups are created as manual requests
  • tracking is updated by staff or by Excel upload

Security

  • Courier API secrets are encrypted (AES-256-GCM) before they are saved. The key is held in AWS KMS, never in the database, and can be rotated.
  • Passwords are stored as argon2id hashes. Login refresh tokens are stored only as hashes.
  • Credentials and personal data are masked before API and webhook logs are written.
  • Every change to rates, credentials, customers, permissions and manual status corrections is written to the audit log.
Section 5

Duplicate protection

Each of these is enforced by a unique rule in the database, so a retried job or a double click can never create a second record.

RiskProtection
Customer double-clicks "Book"One booking per customer per request key
Courier returns an AWB that is already usedOne shipment per courier per AWB
Webhook and poll deliver the same tracking eventEach event is stored once per shipment
A retried job charges the wallet twiceA shipment is charged once and refunded once
A COD amount is remitted or paid out twiceEach shipment appears once in remittances and once in payouts
A payment gateway callback arrives twiceOne record per gateway payment ID
Two workers take the same manual AWBRow locking that skips AWBs another worker has taken
Section 6

Scalability plan

Planning assumption: 10,000 shipments per day. These numbers will be revised once the client confirms expected volume.

TableRows per yearStrategy
shipments~3.6 MIndexed regular table. Comfortable past 50 M rows.
tracking_events~36–50 MMonthly partitions
api_request_logs~50 M+Monthly partitions, keep 6–12 months
webhook_events~30 MMonthly partitions, keep 3–6 months
notification_logs~20 MMonthly partitions
audit_logssmallMonthly partitions, kept long term

Partitioning

The five log tables are split into one partition per month. Removing an old month is instant, where deleting millions of rows would be slow. Before go-live, the pg_partman extension will create future months automatically.

Indexes that stay small

Work queues (shipments still to track, COD not yet settled, shipments not yet invoiced, open tickets, unpaid invoices) use partial indexes that cover only live rows. They stay small however many shipments have been delivered. Admin search uses exact indexes for AWB and mobile number, and fuzzy matching for names.

Fast dashboards

Workers update a daily summary table on every status change. The control tower dashboard and the courier-wise and customer-wise reports read that table, never the full shipments table. Live counters are cached for 30–60 seconds.

Growth path

StageSetup
LaunchOne managed PostgreSQL instance (AWS RDS) with automated backups and point-in-time recovery, plus connection pooling (PgBouncer)
GrowthAdd a read replica for reports, exports and dashboards
ScaleMove heavy logs to their own database, or archive old months to S3
Large scalePartition or shard shipments. Unlikely to be needed below about 100,000 shipments per day.

Cached outside the database (Redis)

  • Serviceable pincodes per service, for 24 hours, cleared when an admin uploads new data
  • Active rate cards per customer, cleared when a rate card is saved
  • Rate quotes shown to a customer, for about 15 minutes, so the booked price matches the quote
  • Public tracking page results, for about 60 seconds

Section 9

Open questions for the client

  1. What daily shipment volume is expected at launch, and after one year? This sets the database size and when a read replica is needed.
  2. Is the company's turnover above the GST e-invoicing threshold? If so, invoices need an IRN.
  3. Are COD payouts to customers made net of freight charges, or in full?
  4. What billing cycle should credit customers have: weekly, fortnightly or monthly?
  5. Should customers be able to create their own sub-users, such as an admin and operators?
  6. Are the retention periods in section 7 acceptable?
